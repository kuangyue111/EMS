# 第一章：系统硬件与软件架构总览

## 1.1 硬件平台深度解析 (S32K146)

系统基于 NXP 的 **S32K146** (车规级 Arm Cortex-M4F, 80MHz)，专为 BMS (Battery Management System) 设计。

### 核心 MCU 与外设拓扑

```text
       ┌──────────────────────────────────────────────────────────┐
       │                  S32K146 (Main MCU, 80MHz)               │
       │                                                          │
       │  ┌───────────┐  ┌──────────┐  ┌──────────────┐          │
       │  │ FlexCAN x3│  │ LPUART x3│  │   FTM 1/3    │          │
       │  │ 500kbps   │  │ RS485    │  │ (0.1ms/1ms)  │          │
       │  └─────┬─────┘  └────┬─────┘  └──────────────┘          │
       │        │              │                                  │
       │  ┌─────▼─────┐  ┌────▼─────┐  ┌──────────────┐          │
       │  │  SPI 0    │  │  SPI 1   │  │   SPI 2      │          │
       │  │ (FS6503)  │  │(LTC2949) │  │ (LTC6813)    │          │
       │  └─────┬─────┘  └────┬─────┘  └──────┬───────┘          │
       │        │              │               │                  │
       └────────┼──────────────┼───────────────┼──────────────────┘
                │              │ (菊花链)      │
                ▼              ▼               ▼
        ┌──────────┐   ┌──────────┐     ┌──────────┐
        │ FS6503   │   │ LTC2949  │     │ LTC6813  │
        │ (SBC)    │   │(库仑计)  │     │ (AFE)    │
        └──────────┘   └──────────┘     └──────────┘
        看门狗/电源      总压/分流器      电芯电压
```

*   **FlexCAN x3**: CAN0 (外网), CAN1 (从控), CAN2 (充电/PCS)。
*   **LPUART x3**: SCI0 (Modbus-1), SCI1 (Modbus-2), SCI2 (预留)。
*   **FTM1**: 0.1ms 定时器，严格用于 Modbus 帧间隔计时 (t3.5)。
*   **FTM3**: 1ms 定时器，系统心跳，**必须**用于电流积分。

## 1.2 软件分层架构图

```text
   ┌─────────────────────────────────────────────────────────┐
   │  App (业务逻辑): Funtion/, Logics/, PileSys/            │
   │  包含: SOC, 状态机，故障诊断，CAN/Modbus 协议解析       │
   └──────────────────────────▲──────────────────────────────┘
                              │ 调用统一 API
   ┌──────────────────────────┴──────────────────────────────┐
   │  User API (中间层): BSPUser/, OSUser/                   │
   │  屏蔽底层差异: BSPCANInit(), DEVADCGetSampAD()           │
   └──────────────────────────▲──────────────────────────────┘
                              │ 直接操作硬件寄存器
   ┌──────────────────────────┴──────────────────────────────┐
   │  Driver / Device (硬件驱动): BSPSys/                    │
   │  MCU 驱动: UART, CAN, SPI, FTM                          │
   │  外设驱动: FS6503, LTC6813, LTC2949, SST26              │
   └─────────────────────────────────────────────────────────┘
```

### 💡 1.3 设计哲学 (Why?)：为什么要这样分层？

**Q: 为什么业务代码不直接操作寄存器 (如直接写 `CAN0_MCR`)?**  
**A: 为了隔离“变”与“不变”**。
1.  **场景**: BMS 开发周期长，硬件变更 (换 MCU 或换 AFE 芯片) 是常态。
2.  **不分层**: 如果业务逻辑（SOC/保护/通信）混杂寄存器操作，更换 MCU 意味着必须重写 SOC 和通信代码，工作量巨大且易产生 Bug。
3.  **分层 (现状)**:
    *   **Device 层**: 专门处理不同芯片的差异 (如 LTC6813 的初始化 vs 国产替代)。
    *   **Driver 层**: 专门处理 MCU 的差异 (S32K 的 CAN 寄存器 vs STM32 的 CAN 寄存器)。
    *   **BSPUser 层**: 提供统一接口。
    *   **App 层**: 纯逻辑，**不依赖任何特定硬件**。
4.  **结果**: 即使底层硬件全换，应用层代码通常无需改动（或仅需极少量修改），极大降低了维护成本。

# 第二章：系统启动完整流程 (代码级追踪)

系统上电后，经历由 汇编启动代码 -> C main 入口 -> 硬件初始化 -> 软件初始化 -> OS 启动 的严密过程。

## 2.1 阶段一：硬件复位与启动代码 (Reset Handler)

**文件位置**: `Project_Settings/Startup_Code/startup_S32K146.S`

**执行流**:
1.  **MSP 设置**: 栈指针指向 RAM 顶部。
2.  **段初始化**:
    *   `.data` (已初始化全局变量): 从 Flash 拷贝到 RAM。
    *   `.bss` (未初始化变量): **清零**。这是极其关键的一步，确保所有标志位 (Flags)、计数器 (Counters) 初始值为 0。
3.  **SystemInit**: 配置 Flash Wait States，启用外部 16MHz 晶振 (OSC)。
4.  **调用 main**: `bl main`。

## 2.2 阶段二：BSP 配置加载 (BSPUserCfgInit)

**入口**: `main()` -> `BSPUserCfgInit()`
**文件**: `Sources/BSPSys/BSPCfg/BSPConfig.c`

```c
void BSPUserCfgInit(void) {
    // 1. 将 BSPConfig.h 中的编译宏映射到运行时结构体 gBSPFunCfg
    // 这样代码可以在运行时动态知道当前开启了哪些模块
    gBSPFunCfg.Bit.FTM1_FUN_EN = FTM1_FUN_EN; // 0.1ms 定时器使能
    gBSPFunCfg.Bit.FTM3_FUN_EN = FTM3_FUN_EN; // 1ms 定时器使能
    gBSPFunCfg.Bit.CAN0_FUN_EN = CAN0_FUN_EN;
    
    // 2. 初始化参数配置结构体 gBSPParaCfg (晶振频率、波特率等)
    gBSPParaCfg.extOsc = 16000000;   // 16MHz
    gBSPParaCfg.can0Rate = 500000;   // 500kbps
    gBSPParaCfg.sci0Baudrate = 19200;// 19.2kbps
}
```
**意义**: 允许代码在运行时根据配置动态决定初始化哪些外设，便于不同项目复用同一套代码。

## 2.3 阶段三：MCU 外设驱动初始化 (BSPDriverInit)

**入口**: `main()` -> `BSPDriverInit()`
**执行顺序** (严格依赖关系，不可乱序):

1.  **看门狗 (WDOG)**: 
    *   配置 `WDOG_TOVAL` 寄存器和 `WDOG_PRESC`。
    *   **关键**: 立即调用 `BSPWatchDogTask()` 喂狗。否则后续初始化耗时过长会导致芯片复位死循环。
2.  **时钟 (CRG/MCG)**: PLL 锁频到 80MHz。
3.  **UART (SCI) 初始化**: SCI0/SCI1/SCI2 配置波特率，使能接收中断 `C2[RIE]`。
4.  **定时器 (FTM) 初始化**: 
    *   FTM1 (0.1ms): 配置 `MOD` 值，使能溢出中断。
    *   FTM3 (1ms): 配置 `MOD` 值，使能溢出中断。
5.  **CAN 控制器初始化**: 配置邮箱掩码，初始化环形队列。
6.  **SPI 控制器初始化**: SPI0/1/2/3 初始化。

## 2.4 阶段四：外部专用芯片驱动 (DEVDriverInit)

此阶段探测并初始化挂在 MCU 外部总线上的芯片：
1.  **FS6503 (SBC)**: SPI0 通信握手，确认芯片在线。
2.  **RTC (RX-8010)**: I2C 读取时间，检查时钟是否跑飞。
3.  **EEPROM (M24512)**: I2C 读取标志位验证 EEPROM 完好。
4.  **Flash (SST26VF064)**: SPI3 读取 JEDEC ID (0xBF2643)。

## 2.5 阶段五：临界区初始化 (关键!)

### 2.5.1 `BSPDisIRQUserInit()` (关中断)
**代码**: `INT_SYS_DisableIRQGlobal();`
**目的**: 此时系统处于临界区。我们在做大量的内存拷贝、链表初始化、传感器寄存器配置，**绝对不能被中断打断**。如果被 1ms 中断打断，中断服务程序读取到只初始化了一半的变量，会导致灾难性的计算错误或状态机乱序。

**执行内容**:
*   参数加载：从 EEPROM 读取配置参数，校验 CRC32。
*   传感器底层配置：初始化 LTC6813, LTC2949。
*   通信库状态机复位。

### 2.5.2 `BSPEnIRQUserInit()` (开中断)
**代码**: `INT_SYS_EnableIRQGlobal();`
**后果**: 此时 FTM1 (0.1ms) 和 FTM3 (1ms) 开始触发中断！
**执行内容**:
*   BootLoaderInit: 检查是否进入升级模式。
*   CalibrationInit: 加载标定系数。
*   SocSoeInit: 恢复 SOC 记忆值。

### 💡 2.6 设计哲学 (Why?)：为什么要有关中断区？
如果不分段，所有初始化都在开中断状态下运行：
*   读取 EEPROM (I2C 慢速) -> 耗时 50ms。
*   这期间 FTM3 发生了 50 次 1ms 中断。
*   电流积分任务读取到未初始化的 K/B 系数 (默认 0)，计算出错误电流。
*   **结论**: 必须关中断保证“数据一致性”。

## 2.7 阶段六：RTOS 调度器启动

**入口**: `RtosTaskStart()` -> `vTaskStartScheduler()`

1.  **创建 11 个 AutoReload Timers**: 周期 2ms~2000ms。
2.  **创建常驻 Tasks**: 采样、CAN、UART。
3.  **启动调度器**: OS 接管 CPU。

# 第三章：中断处理机制 (ISR) 与数据流向

## 3.1 FTM1 (0.1ms) — Modbus 时序驱动

**频率**: 10 kHz
**代码回调**: `Time_ISR_Hook(eFTM1)` -> `ModbusRcvTickTask()`

**流程图**:
```text
[0.1ms 计时器到期]
   │
   └── ModbusRcvTickTask()
         ├── 检查波特率对应的 t3.5 时间 (19.2kbps 下约 2ms)
         ├── 若收到字节，计时器清零
         └── 若无字节，计时器 ++
               └── 超过阈值? -> 标记 "Modbus 帧结束" (Frame Ready)
```

## 3.2 FTM3 (1ms) — 系统心跳中枢

**频率**: 1 kHz
**代码回调**: `Time_ISR_Hook(eFTM3)`

**包含的 4 个关键任务 (必须极快执行)**:
1.  `ISRCurrCapAddTask()`: ★ **电流积分 (Ah Counting)**。必须在 1ms 精确触发，否则 SOC 漂移。
2.  `SysClockCountTask()`: 毫秒/秒计数。
3.  `MbClientTimerTask()`: Modbus 主机状态驱动。
4.  `CANLibTxRcvHandleTask_API()`: CAN 协议栈处理 (多帧超时检测等)。

### 💡 3.3 设计哲学 (Why?)：为什么电流积分必须放在 ISR？
SOC 的核心公式是 $SOC(t) = SOC(t-1) + \frac{I \times \Delta t}{3600}$。
如果放在 RTOS 任务中，由于任务切换的抖动 (Jitter)，$\Delta t$ 就不严格等于 1ms。长时间累积，SOC 误差会越来越大。放在硬件中断中保证了 $\Delta t$ 严格等于 1ms，这是 BMS 精度的基石。

## 3.4 CAN 收发中断
*   **Rx**: 从硬件邮箱拷贝帧到环形队列 -> 释放信号量唤醒 CAN Task。
*   **Tx**: 检查发送队列，写入邮箱，触发发送。
*   **错误**: Bus Off 检测与自动恢复。

## 3.5 SCI (UART) 字节收发
*   **Rx**: UART ISR 收到 1 字节 -> 存入 `sUartRxBuffer`。
*   **解析**: 依赖 FTM1 的 t3.5 超时判断帧结束。

### 💡 3.6 设计哲学 (Why?)：为什么 UART ISR 不做协议解析？
*   **原因**: UART 中断是“每收到一个字节”触发一次。解析 Modbus 需要判断帧头、功能码、CRC，耗时较长。
*   **风险**: 如果在 ISR 做解析，总线负载高时，ISR 执行时间变长，可能阻塞 0.1ms 的 FTM1 中断 (Modbus 计时)，导致“帧切割”错误。
*   **方案**: ISR 只搬运字节，复杂逻辑交给 `UART Rcv Task` (阻塞等待)。

# 第四章：FreeRTOS 任务调度模型 (Timer vs Task)

## 4.1 调度架构设计原则

*   **ISR**: 处理微秒 (us) 级硬实时 (积分、Modbus 时序)。
*   **Timer Callbacks**: 处理毫秒 (ms) 级周期性业务 (限流、滤波、SOC)。
*   **Tasks**: 处理耗时较长、需要阻塞等待的操作 (LTC6813 采样、Modbus 解析)。

## 4.2 `Task10ms` + 10 步轮询器 (核心调度器)

**设计意图**: 将大量 100ms 任务打散到 10 个 10ms 片段中执行。

```text
Task10ms 被调用 (每 10ms 一次)
    │
    ├── sTime = 0 (10ms):  [限流计算] (查表：温度/SOC 降额)
    ├── sTime = 1 (20ms):  [特征检查] (电压极值、温差、平均电流)
    ├── sTime = 2 (30ms):  [故障生成 1] (电压/温度/电流越限)
    ├── sTime = 3 (40ms):  [故障生成 2] (IO/信息异常)
    ├── sTime = 4 (50ms):  [故障生成 3] + [显示更新]
    ├── sTime = 5 (60ms):  [SOC 计算] ★ (读积分值计算电量)
    ├── sTime = 6 (70ms):  [SOH 计算] + [能量显示]
    ├── sTime = 7 (80ms):  [均衡策略] + [PWM 捕获]
    ├── sTime = 8 (90ms):  [绝缘检测] + [保护状态更新]
    └── sTime = 9 (100ms): [接触器检查] + [快充报文组包]
```

### 💡 4.3 设计哲学 (Why?)：为什么要打散任务？
**问题**: 为什么不让所有任务都在 Task100ms 里运行？
**答案**: 为了避免 **CPU 峰值 (Spikes)**。
如果 10 个任务堆积在 100ms 这一刻同时运行，CPU 可能瞬间忙碌 8ms，导致系统卡顿。打散后，CPU 负载曲线平坦 (Flat)，系统响应更灵敏。

## 4.4 软件定时器调度表 (2ms - 2000ms)

| 周期 | 任务名称 | 核心职责 | 关键逻辑 |
| :--- | :--- | :--- | :--- |
| **2ms** | `Task2ms` | Modbus 触发发送 | 准备数据，启动 UART 发送 |
| **5ms** | `Task5ms` | CAN 协议栈处理 | 组装广播报文，检查心跳 |
| **10ms** | `Task10ms` | **系统主调度器** | 见上文轮询器 |
| **50ms** | `Task50ms` | **故障滤波 & 校正** | 消抖，SOC 满充/放空校正 |
| **100ms** | `Task100ms` | **状态机 & 保护** | SOS 计算，根据 SOS 执行动作 |
| **300ms** | `Task300ms` | 容量/能量统计 | 累计历史数据 |
| **500ms** | `Task500ms` | 快充 (GB/T 27930) | 与充电机握手/状态更新 |
| **1000ms** | `Task1000ms` | 交互 & 记录 | 按键检测，外部 Flash 巡检 |
| **2000ms** | `Task2000ms` | **掉电保护** | 欠压关机判定 |

## 4.5 常驻并发任务 (Tasks)

1.  **`CellInfoSampleTask` (Pri 18)**: 发送 LTC6813 转换指令 -> 延时 -> 读电压 -> 存数组 -> 延时循环。
2.  **`HigInfoSampleTask` (Pri 14)**: 读 LTC2949 电流/总压 -> 存数组 -> 延时循环。
3.  **`BSPCANRcvTask` (Pri 15)**: 阻塞等待信号量 -> 收到帧 -> 解析 (广播/查询/设置) -> 回复。

# 第五章：核心算法运行数据流 (Dataflow & FSM)

## 5.1 SOC/SOE 计算全流程 (算法闭环)

```text
[1. 积分 (1ms FTM3 ISR)] -> 累加 Ah -> 存入 g_sCapInt
      │
[2. 计算 (Task10ms Case 5)]
      ├── 获取 Delta_Ah -> 查表补偿 (温度、倍率)
      └── SOC = 剩余容量 / 标定总容量 * 100%
      │
[3. 校正 (Task50ms)]
      ├── 满充校正: V_Max > 3.65V -> SOC = 99.3%
      └── 放空校正: V_Min < 2.50V -> SOC = 0.0%
      │
[4. 滤波 (Display Layer)]
      └── 限制显示变化率 (Max 1%/s)
```

### 💡 5.1 设计哲学 (Why?)：纯 OCV 还是纯积分？
*   **纯开路电压 (OCV)**: LFP 电池平台期电压几乎不变，无法准确反映电量。
*   **纯积分**: 传感器漂移和自放电会导致累积误差，时间久了不准。
*   **方案**: “开环积分（日常准） + 端点校正（长期准）”。

## 5.2 故障诊断四级流水线 (核心亮点)

这是系统中最优秀的架构设计之一。

```text
[ 第 1 级：生成 (Maker) ] @ 10ms
  采样值 vs 阈值
  生成原始标志: Fault_Raw = 1 (可能有瞬态干扰)
       │
       ▼
[ 第 2 级：滤波 (Filter) ] @ 50ms
  引入状态机:
  IF (Fault_Raw == 1) Timer_On++; 
     IF (Timer_On > 2000ms) -> 确认故障!
  此步骤消除了高频毛刺导致的误动作
       │
       ▼
[ 第 3 级：评估 (SOS) ] @ 100ms
  汇总所有已确认故障
  SOS 0: 正常
  SOS 1: 警告
  SOS 2: 降额 (限制电流)
  SOS 3: 停机 (切断接触器)
  SOS 4: 锁定 (人工干预)
       │
       ▼
[ 第 4 级：执行 (Protect) ] @ 100ms
  根据 SOS 等级驱动硬件 (GPIO/Relay)
  同时切断接触器并报警
```

### 💡 5.2 设计哲学 (Why?)：为什么不直接切断？
*   **场景**: 大电流接触器闭合瞬间，电网上会产生 2-3ms 的电压尖峰。
*   **直接判定**: 系统误判“过压”切断接触器 -> 用户发现一上电就掉电，系统不可用。
*   **四级流水线**: 尖峰会被第二级的“延时确认”过滤掉，而真正的长时过压（如 2s）才会触发 SOS=3 停机。

## 5.3 电芯均衡策略 (Balancing)

**策略**: 被动放电 (电阻耗散)。
**判定**: 积分制 (长期偏差)。
*   **逻辑**: 压差持续存在超过一定时间（如 60s），才开启均衡。
*   **安全限制**: 温度 > 80°C 强制关闭均衡；> 60°C 限制均衡数量（最多 8 路）。

## 5.4 绝缘检测与接触器粘连

**绝缘**: 桥式电路法 (切换正/负电阻) 计算对地绝缘电阻。
**粘连**: 断开接触器后检测两端电压。若压差为 0，说明触点熔焊。

# 第六章：通信协议栈运行逻辑

## 6.1 CAN 通信：队列与信号量模型

```text
[接收] CAN ISR -> 存入 Ring Buffer -> 释放信号量
          │ (唤醒 Task)
          └──────> CAN Rcv Task: 取帧 -> 解析 29-bit ID -> 处理逻辑 (读/写/广播)
[发送] 业务层 -> 组包 -> 压入 Tx Queue -> CAN Send Task: 轮询队列 -> 写入硬件邮箱
```

### 💡 6.1 设计哲学 (Why?)：为什么 CAN 处理要放在 Task？
*   **原因**: ISR 不可阻塞，且上下文切换代价高。CAN 协议解析 (如查参数表、写 EEPROM) 耗时长。
*   **收益**: “生产者 (ISR) - 消费者 (Task)” 模型。ISR 只花几微秒搬运数据，繁重的解析交给 RTOS 任务，确保系统实时性。

## 6.2 Modbus RTU：流式解析机制 (RS485)
1.  UART ISR 收字节。
2.  FTM1 ISR (0.1ms) 检测 t3.5 超时 -> 标记 `Frame_Ready`。
3.  Task 检查 `Frame_Ready` -> 校验 CRC -> 查 ModbusMap (6500+ 寄存器) -> 响应。

## 6.3 GB/T 27930 快充状态机
严格的 8 阶段握手：物理连接 -> 握手 (CRM/BHM) -> 配置 (CP/CML) -> 充电 -> 结束。超时监控 (Timeouts) 是核心。

# 第七章：架构深度分析与缺陷诊断

## 7.1 当前设计的核心优势

1.  **高实时性与高精度 (Real-Time Precision)**
    *   **表现**: 电流积分放在严格 1ms 的 FTM3 硬件中断中。
    *   **优势**: 不受 RTOS 任务调度抖动的影响，确保了 SOC 计算的基准精度。

2.  **平滑的负载模型 (Smooth CPU Load)**
    *   **表现**: `Task10ms` 使用 10 步轮询器 (Round-Robin Wheel) 将 100ms 的任务打散执行。
    *   **优势**: 避免了系统每 100ms 出现一次 CPU 峰值 (Spike)，使得中断响应更稳定。

3.  **健壮的故障处理 (Robust Diagnosis)**
    *   **表现**: 采用 "生成 -> 滤波 -> 评估 -> 执行" 的四级流水线。
    *   **优势**: 完美解决了工业现场的“误动作”问题。滤波器可以过滤掉接触器吸合瞬间的电压尖峰。

4.  **极强的解耦性 (Decoupling)**
    *   **表现**: BSP Driver / BSPUser / Application 三层分离。
    *   **优势**: 代码复用率高。换 MCU 或换芯片只需改底层，业务逻辑不动。

## 7.2 当前架构的缺陷与潜在风险 (Critical Analysis)

尽管架构设计优良，但以下 **缺陷 (Defects)** 可能会随着迭代成为隐患：

### ❌ 缺陷 1: ISR (中断) 负载过重
*   **现象**: 1ms FTM3 中断里运行了 `ISRCurrCapAddTask`, `CANLibTxRcvHandleTask_API()` (协议栈处理) 等。
*   **风险**: 如果 CAN 通信繁忙，ISR 执行时间可能接近 1ms。导致重入 (Reentry)，系统死机或 SOC 漂移。
*   **评价**: 定时炸弹。

### ❌ 缺陷 2: 硬编码 (Hard Coding) 现象严重
*   **现象**: 魔法数字 (Magic Numbers) 散落在代码中 (如 `if (SOC > 95 && Curr < 200)` 中的 95 和 200)。
*   **风险**: 修改阈值需要改多处代码，容易漏改或改错。Modbus 映射使用巨大的 `switch-case` (6500+ 寄存器)，维护困难。

### ❌ 缺陷 3: 全局变量泛滥 (Global Variables)
*   **现象**: 模块间通过海量的 `extern u16 gGxxx[]` 数组交换数据。
*   **风险**: 缺乏系统级的互斥锁 (Mutex)。ISR、Timer、Task 同时读写同一份变量，容易出现数据竞争 (Data Race)。

### ❌ 缺陷 4: 缺乏"应用级看门狗"
*   **现象**: 系统只有 FS6503 硬件看门狗。
*   **风险**: 如果 RTOS 任务 (如均衡任务) 陷入死循环，硬件看门狗可能检测不到 (因为 ISR 还在跑，还在喂狗)。系统表面活着，实际瘫痪。
