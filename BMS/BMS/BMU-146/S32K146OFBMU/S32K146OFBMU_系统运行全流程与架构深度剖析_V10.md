# 第一章：系统硬件与软件架构总览

## 1.1 硬件平台深度解析 (S32K146)

系统基于 NXP 的 **S32K146** (车规级 Arm Cortex-M4F, 80MHz)，专为 BMS (Battery Management System) 设计。

### 核心 MCU 与外设拓扑

```text
       ┌──────────────────────────────────────────────────────────┐
       │                  S32K146 (Main MCU, 80MHz)               │
       │                                                          │
       │  ┌───────────┐  ┌──────────┐  ┌──────────────┐          │
       │  │ FlexCAN x3│  │ LPUART x3│  │   FTM 1/3    │          │
       │  │ 500kbps   │  │ RS485    │  │ (0.1ms/1ms)  │          │
       │  └─────┬─────┘  └────┬─────┘  └──────────────┘          │
       │        │              │                                  │
       │  ┌─────▼─────┐  ┌────▼─────┐  ┌──────────────┐          │
       │  │  SPI 0    │  │  SPI 1   │  │   SPI 2      │          │
       │  │ (FS6503)  │  │(LTC2949) │  │ (LTC6813)    │          │
       │  └─────┬─────┘  └────┬─────┘  └──────┬───────┘          │
       │        │              │               │                  │
       └────────┼──────────────┼───────────────┼──────────────────┘
                │              │ (菊花链)      │
                ▼              ▼               ▼
        ┌──────────┐   ┌──────────┐     ┌──────────┐
        │ FS6503   │   │ LTC2949  │     │ LTC6813  │
        │ (SBC)    │   │(库仑计)  │     │ (AFE)    │
        └──────────┘   └──────────┘     └──────────┘
        看门狗/电源      总压/分流器      电芯电压
```

*   **FlexCAN x3**: CAN0 (外网), CAN1 (从控), CAN2 (充电/PCS)。
*   **LPUART x3**: SCI0 (Modbus-1), SCI1 (Modbus-2), SCI2 (预留)。
*   **FTM1**: 0.1ms 定时器，严格用于 Modbus 帧间隔计时 (t3.5)。
*   **FTM3**: 1ms 定时器，系统心跳，**必须**用于电流积分。

## 1.2 软件分层架构图

```text
   ┌─────────────────────────────────────────────────────────┐
   │  App (业务逻辑): Funtion/, Logics/, PileSys/            │
   │  包含: SOC, 状态机，故障诊断，CAN/Modbus 协议解析       │
   └──────────────────────────▲──────────────────────────────┘
                              │ 调用统一 API
   ┌──────────────────────────┴──────────────────────────────┐
   │  User API (中间层): BSPUser/, OSUser/                   │
   │  屏蔽底层差异: BSPCANInit(), DEVADCGetSampAD()           │
   └──────────────────────────▲──────────────────────────────┘
                              │ 直接操作硬件寄存器
   ┌──────────────────────────┴──────────────────────────────┐
   │  Driver / Device (硬件驱动): BSPSys/                    │
   │  MCU 驱动: UART, CAN, SPI, FTM                          │
   │  外设驱动: FS6503, LTC6813, LTC2949, SST26              │
   └─────────────────────────────────────────────────────────┘
```

### 💡 1.3 设计哲学：为什么要分层？

**问题**: 为什么业务代码不直接操作寄存器 (如直接写 `CAN0_MCR`)?

**原因**: **为了隔离“变”与“不变”**。
1.  **场景**: BMS 开发周期长，硬件变更 (换 MCU 或换 AFE 芯片) 是常态。
2.  **不分层**: 如果业务逻辑里混有寄存器代码，更换 MCU 需要重写 SOC 和保护逻辑，风险极高。
3.  **分层 (现状)**:
    *   **Device 层**: 适配不同 AFE (LTC6813 vs 国产替代)。
    *   **Driver 层**: 适配不同 MCU (S32K vs STM32)。
    *   **App 层**: **纯逻辑，不依赖任何硬件**。
4.  **收益**: 即使底层硬件全换，上层代码通常无需改动，极大降低维护成本。

# 第二章：系统启动完整流程 (代码级追踪)

系统启动是一个严密的 6 阶段过程。

## 2.1 启动流程图 (Boot Sequence)

```text
[硬件 Reset] -> Reset_Handler (汇编)
      │
      ├── 1. 初始化 MSP (栈指针)
      ├── 2. .data 段搬运 (Flash -> RAM)
      ├── 3. .bss 段清零 (防止随机垃圾值)
      └── 4. 调用 main()
            │
            ├── A. BSP 配置加载 (BSPUserCfgInit)
            │
            ├── B. MCU 驱动初始化 (BSPDriverInit)
            │   ├── Watchdog, Clock (80MHz)
            │   ├── UART/CAN/SPI/FTM
            │   └── Device 探测 (DEVDriverInit)
            │
            ├── C. 临界区初始化 (关键!)
            │   ├── 关中断 (CPSID i)
            │   ├── 加载 EEPROM 参数
            │   ├── 初始化队列/状态
            │   └── 开中断 (CPSIE i)
            │
            └── D. OS 启动 (RtosTaskStart)
                ├── 创建 11 个定时器
                ├── 创建 6 个常驻任务
                └── 启动调度器 (Main 永不返回)
```

## 2.2 阶段一：硬件复位与向量表

**代码位置**: `startup_S32K146.S`
CPU 复位后从 `0x00000000` 读 SP，从 `0x00000004` 读 PC。

**关键动作**:
1.  **SystemInit()**: 启动外部 16MHz 晶振，配置 PLL 倍频锁相环至 **80 MHz**。
2.  **段初始化**: `.bss` 清零至关重要，确保所有的 Flag (状态标志) 初始为 0，否则上电可能误触发保护。

## 2.3 阶段二：BSP 配置加载

**文件**: `BSPCfg/BSPConfig.c` -> `BSPUserCfgInit()`
**目的**: 将编译宏映射到运行时结构体。
```c
// 使得代码在运行时能动态检查模块是否使能
gBSPFunCfg.Bit.FTM1_FUN_EN = FTM1_FUN_EN;
gBSPParaCfg.extOsc = 16000000;
gBSPParaCfg.sci0Baudrate = 19200;
```

## 2.4 阶段三：MCU 驱动初始化

**文件**: `BSPCfg/BSPConfig.c` -> `BSPDriverInit()`
**顺序**:
1.  **看门狗 (WDOG)**: 立即配置并**首次喂狗**。如果不喂，后续初始化耗时过长会导致芯片复位。
2.  **时钟 (CRG)**: 开启外设时钟门控 (PCC)。
3.  **通信**: 初始化 UART (19200bps) 和 CAN (500kbps)。
4.  **定时器**: 
    *   FTM1 设为 **0.1ms** 中断 (Modbus 计时)。
    *   FTM3 设为 **1ms** 中断 (系统心跳)。
5.  **SPI/I2C**: 初始化 SPI0~3。

**探测**: `DEVDriverInit()` 
通过 SPI/I2C 读取外部芯片 ID (如 FS6503, SST26) 确认设备在线。

## 2.5 阶段四：外部复杂外设探测

此阶段探测外部设备，确保存储和传感器正常。
*   **FS6503**: 配置安全看门狗。
*   **EEPROM**: 读标志位验证。
*   **Flash**: 读取 JEDEC ID 验证。

## 2.6 阶段五：临界区初始化 (关键!)

这是系统稳定性的核心。

**动作 1: 关全局中断 (`INT_SYS_DisableIRQGlobal`)**
*   **原因**: 此时系统加载 EEPROM 参数和初始化内存。如果此时 FTM3 的 1ms 中断触发，中断程序读取到“写了一半”的阈值参数，会导致误保护或崩溃。
*   **执行内容 (`BSPDisIRQUserInit`)**:
    1.  读取 EEPROM 参数，校验 CRC。
    2.  复位所有通信队列。
    3.  清零故障标志。
    4.  配置 LTC6813 AFE 寄存器。

**动作 2: 开全局中断 (`INT_SYS_EnableIRQGlobal`)**
*   **后果**: FTM1 和 FTM3 立即开始产生中断！
*   **执行内容 (`BSPEnIRQUserInit`)**:
    1.  加载标定 K/B 系数。
    2.  恢复 SOC 记忆值。

### 💡 2.6.3 设计哲学：为什么要分两段 (关/开)？

如果不分段，所有初始化都在开中断状态下运行：
*   读取 EEPROM (I2C 慢速) -> 耗时 50ms。
*   这期间 FTM3 发生了 50 次 1ms 中断。
*   电流积分任务读取到未初始化的 K/B 系数 (默认 0)，计算出错误电流。
*   **分段的哲学**: 确保数据在“安全状态”下加载，加载完毕后才允许“时间敏感”的中断介入。

## 2.7 阶段六：RTOS 环境创建

**文件**: `OSUser/OSUserHOOK.c` -> `RtosTaskStart()`
1.  创建 **11 个定时器** (Timer 2ms~2000ms)。
2.  创建 **常驻任务** (Tasks): 采样、CAN、UART。
3.  `vTaskStartScheduler()`: 调度器接管 CPU，系统进入多任务并发运行。

# 第三章：中断处理机制 (ISR) 与数据流向

## 3.1 FTM1 (0.1ms) — Modbus 时序驱动

**代码**: `BSPISRHook.c` -> `Time_ISR_Hook(eFTM1)` -> `ModbusRcvTickTask()`

**逻辑**:
```text
[0.1ms 计时器到期]
   │
   └── ModbusRcvTickTask()
         ├── 检查波特率对应的 t3.5 时间
         ├── 若收到字节，计时器清零
         └── 若无字节，计时器 ++
               └── 超过阈值? -> 标记 "Modbus 帧结束" (Frame Ready)
```

### 💡 3.2 设计哲学：为什么不把 Modbus 解析放在 UART 中断里？

*   **原因**: UART 中断是“每收到一个字节”触发一次。但 Modbus 不知道这 1 字节是帧头还是帧尾。它只能靠“两个字节之间隔了多久” (静默时间) 来判断。
*   **方案**: 
    *   **UART ISR**: 只管搬运字节到内存 (极快，几微秒)。
    *   **FTM1 ISR (0.1ms)**: 巡逻员，每 0.1ms 检查一次“距离上个字节过去了多久”。超过 t3.5，判定帧结束。
*   **优势**: 完美处理了 Modbus 不定长帧，且 UART ISR 极短，不会阻塞其他中断。

## 3.3 FTM3 (1ms) — 系统心跳中枢

这是系统最繁忙的中断。

**代码**: `Time_ISR_Hook(eFTM3)`

**执行逻辑**:
1.  **`ISRCurrCapAddTask()`**: 获取电流值，累加到 `Ah_integral`。**必须在 1ms 执行，保证 SOC 精度。**
2.  **`SysClockCountTask()`**: 毫秒/秒计数。
3.  **`MbClientTimerTask()`**: Modbus 主机状态驱动。
4.  **`CANLibTxRcvHandleTask_API()`**: CAN 协议栈处理 (多帧超时检测)。
5.  **`HeartToSlaveMcuTask()`**: 100ms 一次的心跳检查。

### 💡 3.3 设计哲学：为什么电流积分必须放在 ISR？

SOC 的核心公式是 $SOC(t) = SOC(t-1) + \frac{I \times \Delta t}{3600}$。
如果放在 RTOS 任务中，由于任务切换的抖动 (Jitter)，$\Delta t$ 就不严格等于 1ms。长时间累积，SOC 误差会越来越大。放在硬件中断中保证了 $\Delta t$ 严格等于 1ms。

## 3.4 CAN 收发与错误中断

*   **Rx 中断**: 
    1. 从硬件邮箱拷贝帧到环形队列 (Ring Buffer)。
    2. **释放信号量** (`xSemaphoreGiveFromISR`) 唤醒 CAN 接收任务。
    3. **解析逻辑不放在这里** (见 6.1)。
*   **Tx 完成中断**: 检查队列是否有下一帧，触发发送。

# 第四章：FreeRTOS 任务调度模型

## 4.1 10ms 轮询器 (Time Slicing) 运行逻辑图

在 `Task10ms` 中，系统没有一次性执行完所有任务，而是使用了一个 10 步轮询器 (`switch(sTime)`, sTime 从 0 到 9)。**这 10 步加起来构成 100ms 的完整业务循环**。

```text
Task10ms 被调用 (每 10ms 一次)
    │
    ├── sTime = 0 (10ms):  执行 [限流计算] -> return (耗时约 0.2ms)
    ├── sTime = 1 (20ms):  执行 [特征检查] -> return (耗时约 0.1ms)
    ├── sTime = 2 (30ms):  执行 [故障生成 1] -> return
    ├── sTime = 3 (40ms):  执行 [故障生成 2] -> return
    ├── sTime = 4 (50ms):  执行 [故障生成 3] -> return
    ├── sTime = 5 (60ms):  执行 [SOC 计算] -> return (耗时约 0.5ms)
    ├── sTime = 6 (70ms):  执行 [SOH 计算] -> return
    ├── sTime = 7 (80ms):  执行 [均衡策略] -> return
    ├── sTime = 8 (90ms):  执行 [绝缘/保护] -> return
    ├── sTime = 9 (100ms): 执行 [接触器检查] -> return
    └── sTime 回到 0
```

### 💡 4.4 设计哲学：为什么要打散任务？

**问题**: 为什么不让所有任务都在 Task100ms 里一次性运行？
**答案**: 为了避免 **CPU 峰值 (Spikes)** 和 **优先级反转**。
1.  **平滑负载**: 如果 10 个任务堆积在 100ms 这一刻同时运行，CPU 可能瞬间忙碌 8ms，导致这段时间内 1ms 的 FTM3 中断响应延迟，甚至引起系统卡顿。
2.  **摊薄后**: 每个 10ms 片段只干一点点活，CPU 占用率非常平稳，系统响应更灵敏。

## 4.2 软件定时器调度表 (全景)

| 周期 | 任务 | 核心职责 | 关键逻辑说明 |
| :--- | :--- | :--- | :--- |
| **2ms** | Modbus 触发 | Modbus 响应发送 | 准备数据，启动 UART 发送 |
| **5ms** | CAN 协议栈 | 报文收发，心跳检测 | 组装 1s 广播报文，检查从控存活 |
| **10ms** | **核心轮询器** | 限流/均衡/SOC/诊断 | 见 4.1 节，系统逻辑的大本营 |
| **50ms** | **故障滤波** | 信号消抖 (Filter) | 区分"真实故障"与"毛刺干扰" (见 5.2) |
| **50ms** | SOC 高级库 | 端点校正，包间同步 | SOC=100% 或 0% 时的强制对齐逻辑 |
| **100ms** | **保护执行** | SOS 计算，状态机 | 根据故障等级决定是否断开接触器 |
| **300ms** | 统计记录 | 循环次数，容量统计 | 低频写入 EEPROM 的数据处理 |
| **500ms** | 快充协议 | GB/T 27930 状态机 | 与充电机通信握手 |
| **1000ms** | 交互逻辑 | 按键消抖，时钟记录 | 人机交互处理 |
| **2000ms** | **掉电保护** | 欠压关机判定 | 极低频率检查电池是否过度放电 |
